Date: 2026-10-04
Branch: `feature/chat-worksheet-lite`
Source of truth: `docs/superpowers/specs/2026-10-04-chat-worksheet-lite-design.md`
Status: Ready for execution

This plan is Markdown only. It does not implement application code. Each task is written so an
independent agent can execute it with the spec open beside it.

---

## 1. Objective

Ship the approved design: turn the current original 2-file app (`server.js` Express + Anthropic
proxy, `index.html` single-page chat UI) into a two-path learner app under `public/`:

- **Chat** — the existing tutor ported with **zero behavior change**.
- **Worksheet** — AI-generated A1 worksheet (listening / reading / translation-grammar /
  writing) answered in-browser, autosaved to `localStorage`, with a TTS listening section cached
  in IndexedDB, and "send to teacher" feedback rendered adjacent to each answer.

The server becomes a **minimal key proxy**: static serving plus `/api/chat`, `/api/generate`,
`/api/tts`, `/api/feedback`, `/health`. Text provider `ollama` (default, Ollama Cloud) or
`openai`; TTS via OpenAI. Keys stay server-side only. No DB, auth, Supabase, Notion, or jobs.

**Trust model (state plainly, in code comments and README):** this is a personal practice tool,
not a secure exam. Generated answers, listening transcripts, and the answer key are delivered in
the `/api/generate` payload and held in the browser so the learner can reveal them. There is no
server-side grading secrecy. The transcript/answers are *hidden from the rendered UI* until
reveal, not cryptographically protected from a curious learner using DevTools. Feedback is
generated by an AI teacher, not an invigilator.

### Phase 0 — Scaffolding & project hygiene

**Task 0.1 — Create `public/` shell and move static assets.**
- Create `public/index.html`: keep the existing `<head>` (viewport meta with
  `interactive-widget=resizes-content`, favicon data-URI SVG, Google Fonts preconnect + DM Sans
  / Playfair Display link). Replace inline `<style>` with `<link rel="stylesheet"
  href="/styles.css">`. Body holds: the password gate markup (ported), a header/logo/tagline, a
  nav or landing container, and `<main id="view">`. Load `<script type="module" src="/app.js">`.
- Preserve the exact `.gate` markup/ids so the gate logic port (Task 2.1) can reuse it.
- Acceptance: `GET /` returns the shell; no inline CSS remains; fonts and favicon unchanged.

**Task 0.2 — Extract `public/styles.css`.**
- Copy the entire `<style>` block (index.html lines 25–645) into `public/styles.css` verbatim,
  including the `:root` custom properties (`--bg #1a1a2e`, `--panel #22223a`, `--panel-2
  #2a2a45`, `--gold #f5c842`, `--coral #ff8c69`, `--green #7bd88f`, `--text`, `--muted`,
  `--bubble-teacher`, `--bubble-student`, `--border`), the `.logo` Playfair Display styling,
  gate, chat, correction, voice-status, pause-inline, and `.session-counter` rules.
- Add new worksheet/landing styles at the end of the same file, reusing the CSS variables:
  landing cards, section cards with French title + English explanation, question blocks,
  autosave status (`.save-state` with saving/saved/failed variants and text labels, not color
  alone), hint/reveal buttons, feedback blocks adjacent to answers (`.feedback` with
  verdict/correction/explanation labels), summary card, listening player controls
  (play/replay/slow/transcript toggle), and `.audio-unavailable` notice.
- Do not rename or alter existing selectors used by the ported chat.
- Acceptance: visual smoke of chat view matches pre-port screenshots; new classes defined.

**Task 0.3 — Hash router + bootstrap (`public/app.js`).**
- Implement a minimal hash router: routes `#/` → landing, `#/chat` → chat, `#/worksheet` →
  worksheet. On `hashchange` and initial load, resolve the view, tear down the previous view
  (call its optional `destroy()`), and mount the new one into `#view`.
- Unknown/empty hash → redirect to `#/`. Preserve deep-linking so refresh/back returns to the
  same view (spec §6.1).
- Views export `{ mount(container, ctx), destroy?() }`; `ctx` exposes `navigate(hash)`, `api`,
  `storage`, `audioCache`, and `authHeaders()`.
- Run app-wide mobile viewport setup (the `--vvh` visualViewport sync) once here, or expose it
  from a shared helper used by chat (Task 2.1). Prefer keeping it in `app.js` so it applies to
  all views; ensure chat's `pinToBottom` can still call it.
- Acceptance: manually navigating hash values mounts the correct view; refresh keeps view.

**Task 0.4 — `public/lib/api.js` (fetch wrapper).**
- `request(path, { method='POST', body, json=true } = {})` builds headers
  (`Content-Type: application/json`, plus `x-app-password` from storage when present), calls
  `fetch`, reads JSON safely (fall back to `{ error: { message: rawText } }` on parse failure),
  and throws a normalized `ApiError { status, message }` on non-2xx.
- Export typed helpers: `chat(payload)`, `generate(payload)`, `tts(payload)`,
  `feedback(payload)`, `health()`, `authRequired()`, `verifyPassword(pw)`.
- Normalize provider errors so the UI always has a human-readable `.message` (spec §10).
- Acceptance: unit-testable pure functions where possible; no key ever read from the DOM.

**Task 0.5 — `public/lib/storage.js` (versioned localStorage).**
- Wrapper over `localStorage` with safe read (try/catch → default), write that **returns
  success/failure** rather than swallowing, and a schema version key
  `oohlalangue_schema_version`.
- Keys per spec §7: retain `oohlalangue_name`, `oohlalangue_password`, `oohlalangue_profile`,
  `oohlalangue_answers`, `oohlalangue_pause_until` exactly; add
  `oohlalangue_worksheet_current`, `oohlalangue_worksheet_answers`,
  `oohlalangue_worksheet_feedback`, `oohlalangue_schema_version`.
- Provide typed getters/setters: `getName/setName`, `getPassword/setPassword`,
  `getProfile/addProfileFacts`, `getAnswers/setAnswers`, `getPauseUntil/setPauseUntil`,
  `getCurrentWorksheet/setCurrentWorksheet`, `getWorksheetAnswers/setWorksheetAnswers`
  (including last-saved timestamp), `getFeedback/setFeedback`, `clearCurrentWorksheet()`.
- Migration: on load, if stored version is missing/older than `CURRENT_SCHEMA_VERSION`, run
  ordered migrations; unknown/newer version → discard only worksheet keys, never chat keys,
  never crash (spec §7, §12).
- `JSON.parse` failures fall back to empty/`null` and are reported, not thrown.
- Acceptance: existing chat keys round-trip unchanged; a corrupt value does not break app boot.

**Task 0.6 — `public/lib/audio-cache.js` (IndexedDB).**
- Promise-based wrapper over IndexedDB: open DB `oohlalangue_audio`, object store `clips`
  keyed by cache key string; values `{ mime, bytes: ArrayBuffer, createdAt }` (or Blob).
- API: `isAvailable()`, `get(key)`, `put(key, { mime, bytes })`, `delete(key)`,
  `clearAll()`. Key = `hash(script + voice + speed)` — compute the same normalized hash on the
  client and (when the server returns `cache_key`) prefer the server-provided key so client and
  server agree; fall back to a local hash (e.g. FNV-1a/djb2 over a canonicalized string) if
  absent. Document the canonicalization (trim, normalize whitespace, `script|voice|speed`).
- Graceful fallback: if `indexedDB` is missing, blocked, or any operation rejects, resolve to
  `null`/`false` and set an `available=false` flag; callers re-fetch from `/api/tts`. The app
  shows a "caching off" note but keeps playback working (spec §7, §10).
- Store/return the **whole segment list** for a listening script under one `cache_key`.
- Acceptance: unit tests with a fake IndexedDB verify key stability, collision avoidance
  between different speed/voice/script, and unavailable-IndexedDB fallback.

**Phase 0 verification:** `npm start` serves `public/index.html`; landing/chat/worksheet route
stubs mount; styles loaded; `storage.js`/`audio-cache.js` load without console errors.

### Phase 1 — Server rewrite: provider abstraction

**Task 1.1 — Split server internals into a testable module boundary.**
- Extract the existing prompt/curriculum/gate helpers (`CURRICULUM_MODULES`,
  `CURRICULUM_SUMMARY`, `sanitizeName`, `sanitizeFact`, `sanitizeProfile`,
  `buildSystemPrompt`, `trimHistory`) into named functions that are exported (e.g.
  `module.exports = { app, buildSystemPrompt, trimHistory, providers, validateWorksheet,
  validateFeedback, ... }`) so `node:test` can import them without starting the listener.
- Keep `app.listen` guarded so importing the module in tests does not bind the port
  (e.g. only listen when `require.main === module`, or export a `start()` and call it
  conditionally).
- **Do not change the prompt text.** Copy it byte-for-byte, including markers
  `✅ GOOD / 🔧 FIX / 💬 CORRECTED / 🗣️ SAY IT`, the `<note>…</note>` trailer instructions, the
  English-word teach-on translation rule, `skipQuestion`, `voiceMode`, and the A1 rules.
- Acceptance: a test asserts `buildSystemPrompt(...)` output is unchanged for fixed inputs
  (snapshot/golden-string comparison against the pre-change output).

**Task 1.2 — Provider abstraction (`ollamaCloud` default, `openai`).**
- Create a `providers` map keyed by `TEXT_PROVIDER` (`ollama` → ollamaCloud, `openai`).
- Each provider exposes `chatCompletion({ system, messages, maxTokens, timeoutMs })` returning
  `{ text, raw }`; internally uses Node's built-in `https` (consistent with existing code) or
  global `fetch` available on Node ≥18 — pick one and keep it consistent. Recommended: a shared
  `httpJson()` helper using `https`/`http` so behavior is identical across Node versions.
- Ollama Cloud: base URL from `OLLAMA_BASE_URL` (default documented placeholder, e.g.
  `https://ollama.com/api/chat` or the account's documented endpoint), `Authorization: Bearer
  $OLLAMA_API_KEY`, model `OLLAMA_MODEL`. Parse the provider's chat response shape defensively
  (Ollama returns `{ message: { content } }` for `/api/chat`; OpenAI returns
  `choices[0].message.content`).
- OpenAI: `https://api.openai.com/v1/chat/completions`, `Authorization: Bearer
  $OPENAI_API_KEY`, model `OPENAI_MODEL`.
- Provider selection is server-side only; never log or return keys.
- If the selected provider's key is missing → return 500 JSON with an actionable setup message
  naming the env var; never fabricate content (spec §10).
- Acceptance: unit tests mock the HTTP layer and assert correct URL/headers/body per provider,
  and that a missing key yields the actionable error with no outbound call.

**Task 1.3 — `/api/chat` refactor onto the provider abstraction.**
- Keep the request contract `{ messages, name, profile, skipQuestion, voiceMode }` and response
  `{ text, raw }`. Keep the optional `APP_PASSWORD` gate (`checkPassword`, `safeEqual`,
  `/api/auth` GET+POST) exactly.
- Keep `isOpening = messages.length === 1` and `trimHistory(messages, 20)`.
- Add a bounded timeout (e.g. `AI_TIMEOUT_MS`, default 30s) and **exactly one** retry on
  transient failure (network error / 5xx / timeout), then surface the error (spec §10). Do not
  retry 4xx.
- Preserve `skipQuestion`/`voiceMode` → `buildSystemPrompt` wiring and the English-translation
  system-prompt behavior.
- Acceptance: golden test that the built system prompt for representative inputs is unchanged;
  gate behavior tests (401 when wrong password, 200 when open).

**Task 1.4 — `/api/generate` (structured worksheet incl. listening script).**
- Accept `{ topic, level='A1', length, includeListening, name?, profile? }`.
- Instruct the provider to return **strict JSON only** matching spec §9 worksheet shape, with
  `sections` limited to `listening | reading | translation_grammar | writing`, and the `audio`
  block only on the listening section (`script`, `speakers[] {name, voice}`, `cache_key`).
- Server-side validation (`validateWorksheet`): required keys, section ids in the allowed set,
  question `type` in `short_text|choice|fill_blank|translation`, `options` present for choice,
  `answer` present, and — for listening — non-empty script + at least one distinct speaker for
  dialogues. Invalid JSON → one repair retry (re-ask for JSON only), then a clear 502 error; never
  return partial/fabricated content (spec §10).
- **Answer/transcript hiding — be explicit and honest:** the server validates structure and the
  client stores answers for reveal by design. Because there is no server-side grading secrecy,
  the `answer` fields and the listening `script` **are present in the `/api/generate` payload**.
  Hiding is a **UI concern**: `views/worksheet.js` must not render them into the DOM until
  reveal/submit, and the transcript toggle must not exist in the DOM with the text inline. Add a
  code comment and README note stating this trust model plainly. (If a future release wants
  server-side secrecy, grading must move server-side; out of scope here.)
- Compute/normalize `audio.cache_key` server-side as `hash(script + voices)` so the TTS cache
  key is stable across reloads.
- Acceptance: unit tests feed valid and invalid provider JSON; valid returns parsed object,
  invalid triggers repair then 502; listening section shape enforced.

**Task 1.5 — `/api/tts` (per-utterance segments).**
- Accept `{ utterances: [{ speaker, text }], speakers: [{ name, voice }], cache_key }`.
- Require `OPENAI_API_KEY`; if missing → 500 actionable error and the client shows
  "audio unavailable" without fabricating audio (spec §10).
- Synthesize each utterance with its speaker's voice via OpenAI TTS
  (`OPENAI_TTS_MODEL`, voice from `speakers`, default `OPENAI_TTS_VOICE`), returning
  `{ segments: [{ speaker, mime, base64, pause_after_ms }] }` in order. Single-voice narration →
  one segment. Set `pause_after_ms` (e.g. ~600 ms between dialogue turns, 0 on final).
- Bound concurrency (small pool) and enforce a timeout + one bounded retry per utterance.
- Base64 payloads only over the internal API; consider a size guard and clear error if the
  script is too long (documented cap).
- Acceptance: unit tests mock OpenAI and assert per-speaker voice routing, ordered segments,
  pause durations, and missing-key error with no outbound call.

**Task 1.6 — `/api/feedback` (per-answer + summary).**
- Accept `{ worksheet, answers }` (or `{ topic, level, sections, answers }`).
- Instruct provider for strict JSON per spec §9 feedback contract: `answers[]` with
  `question_id, original, verdict in correct|mistake|alternative, correction, explanation,
  error_type in error|style|alternative`, plus `summary { strengths[], recurring_mistakes[],
  priorities[], follow_up }`.
- Validate with `validateFeedback`; preserve `original` from the submitted answer (do not let
  the model rewrite it); one repair retry then clear 502.
- Do not grade listening purely from answers if the transcript is needed — include the script in
  the prompt context server-side (it is already available in the worksheet payload).
- Acceptance: unit tests for valid/invalid shapes and that `original` echoes the learner input.

**Task 1.7 — `/health` and static serving.**
- Serve `public/` via `express.static(path.join(__dirname, 'public'))`; keep `/` → shell and
  `/favicon.ico` 204.
- `GET /health` returns `{ textProvider, textModelConfigured: bool, ttsConfigured: bool,
  passwordRequired: bool, ok }` — **no secret values** (spec §8). Report `ollama` default when
  `TEXT_PROVIDER` unset.
- Startup logs warn (not fail) when keys are missing, mirroring current behavior.
- Acceptance: `curl /health` shows provider/config booleans and no keys; `GET /` serves shell.

**Phase 1 verification:** `npm start`; `/health` correct; `/api/chat` golden prompt unchanged
and works against a stub/mocked provider; `/api/generate`, `/api/tts`, `/api/feedback` happy
paths against mocked providers; missing-key paths return actionable non-fabricated errors.

### Phase III — Worksheet (`views/worksheet.js`)

**Task 3.1 — Generation UI.**
- Choose topic, length, and whether to include the listening section; optional level fixed A1.
- POST `/api/generate`; show a loading state; on error show the server's actionable message.
- On success store via `storage.setCurrentWorksheet(worksheet)`, clear prior answers/feedback,
  then render.

**Task 3.2 — Renderer (textContent only, never innerHTML for model output).**
- Render each section: French `title_fr` + `explanation_en`. Render each question `prompt`
  with proper input control by `type` (`short_text`/`translation` → textarea/input;
  `fill_blank` → input; `choice` → radios/select from `options`).
- **Never** use `innerHTML` for model-derived strings. Create elements and set `.textContent`
  for prompts, options, corrections, explanations, transcript. This is a security requirement
  (spec §9). The ported chat's `mdToHtml` must not be imported here.
- Answer inputs are bound to `storage` autosave (Task 3.3); each input has an aria-label and a
  visible question id/context.
- Acceptance: a malicious provider string containing `<img onerror>` renders as literal text
  (unit or manual check).

**Task 3.3 — Autosave / resume.**
- On input, debounce (~400–800 ms), persist `{ answersByQuestionId, lastSavedAt }` via
  `storage.setWorksheetAnswers`. Show a visible save state: **saving / saved / failed**, with
  **text labels**, not color alone (accessibility, spec §6.3/§10).
- On save failure: keep text in memory, show "failed" + actionable note, never silently drop.
- On view mount, if a current worksheet exists, restore it plus saved answers, feedback, and
  audio cache status (resume, spec §6.3). Restoring must not re-call `/api/generate`.
- Acceptance: type → wait → refresh → same worksheet + answers + saved indicator; simulated
  quota error keeps in-memory text and shows failed.

**Task 3.4 — Hint / reveal.**
- Optional hint control (if the worksheet/prompt includes hint text; otherwise omit gracefully).
- "Show answers" reveals `answer` + `explanation` and, for listening, the transcript. Reveal
  state persists (e.g. in answers payload) so it survives refresh. Answers/transcript are in the
  payload by design (trust model §1) but must not be in the DOM before reveal — verify by
  inspecting the DOM, not just CSS hiding.
- Acceptance: before reveal, no answer/transcript text nodes/serialized DOM; after reveal they
  appear adjacent to the question.

**Task 3.5 — Listening player.**
- On mount, if the worksheet has a `listening` section with `audio`, check
  `audioCache.get(cache_key)`. On hit, play cached segments (no TTS call). On miss, POST
  `/api/tts` with `{ utterances, speakers, cache_key }`, then `audioCache.put(cache_key, …)`.
- Derive `utterances` from the script + speakers (server may also return utterances; if not,
  split the script by speaker turns using the section's structure). Prefer server-provided
  ordered utterances to avoid ambiguity.
- Play segments in order with `pause_after_ms`; support **replay** and **slow** (e.g. playback
  rate 0.75). Provide a "transcript" toggle that is disabled/absent until reveal/submit.
- TTS failure or missing key → render the questions and an **"audio unavailable"** notice with
  the server's actionable message; never play silent/fabricated audio (spec §10).
- IndexedDB unavailable → still fetch and play; show "caching off" note (spec §10).
- Acceptance: first play calls TTS; replay and refresh-play do **not** re-call TTS (verify
  network tab + cache hit); slow/replay work; transcript hidden until reveal.
- Track player cleanup in `destroy()` to stop audio when leaving the view.

**Task 3.6 — Send to teacher + feedback rendering.**
- "Envoyer au professeur" → POST `/api/feedback` with worksheet + answers; disable while
  in-flight; show error actionably on failure.
- Render feedback **adjacent to each answer**: preserve original, correction immediately after,
  explicit **text labels** (`Correct` / `Mistake` / `Alternative`, error type), not color alone.
  Render with `textContent`. Render the concise summary (strengths, recurring mistakes,
  priorities, follow-up) as a labelled summary card.
- Persist feedback via `storage.setFeedback`; restore on resume.
- Acceptance: each answered question shows original + labelled correction + explanation; summary
  visible; refresh keeps feedback.

**Task 3.7 — New worksheet archiving + audio-cache cleanup.**
- "New worksheet" explicitly clears `oohlalangue_worksheet_current`,
  `oohlalangue_worksheet_answers`, `oohlalangue_worksheet_feedback` (archive in memory if
  desired, but not required), and deletes the associated `cache_key` from IndexedDB so clips are
  not orphaned (spec §6.3/§7). If multiple cache keys existed for the worksheet, clear them all.
- Confirmation step before destructive clear.
- Acceptance: after "New worksheet", storage keys gone and `audioCache.get(oldKey)` misses;
  a subsequent play re-bills exactly once.

**Phase III verification:** end-to-end worksheet journey (see §7).

## 5. Potential Risks

1. **Porting a 1517-line inline-CSS app without regressions.** The chat has intertwined gate,
   session-limit, voice, and mobile-viewport logic. Mitigation: port byte-for-byte where
   possible, keep the golden `buildSystemPrompt` test, and run a manual parity checklist against
   the old file before deleting it from the tree.
2. **Keeping the chat prompt/behavior identical.** Any prompt drift changes corrections and the
   `<note>` profile extraction. Mitigation: no prompt edits in this release; snapshot test;
   keep marker regexes and labels unchanged.
3. **TTS latency/cost.** Per-utterance synthesis for dialogues multiplies calls and cost; long
   scripts are slow. Mitigation: bounded concurrency, per-utterance timeout + one retry, IndexedDB
   caching keyed by `cache_key`, and a documented script-length cap. Resume must not re-bill.
4. **IndexedDB/browser variance.** Private mode, storage pressure, and Safari quirks can disable
   IndexedDB. Mitigation: `audio-cache.js` graceful fallback; playback works uncached; UI states
   "caching off"; tests with fake IndexedDB.
5. **Key leakage.** Keys must never reach the browser or `/health`. Mitigation: all provider keys
   read only in `server.js`; `/health` returns booleans only; lint/grep check that no key env var
   is referenced under `public/`.
6. **Trust model — answers live client-side.** The answer key and listening transcript ship in
   the `/api/generate` payload so the learner can reveal them; this is **not** a secure exam and
   provides no server-side grading secrecy. Mitigation: state it plainly in README and code;
   enforce DOM-level hiding until reveal; keep the server as an honest grader/feedback generator,
   not an invigilator.
7. **Malicious/invalid model output.** Structured JSON can be malformed or contain HTML.
   Mitigation: strict validation with one repair retry then 502; `textContent`-only rendering for
   worksheet output; never `innerHTML` model strings.
8. **Provider/model name uncertainty (spec §13).** `OLLAMA_MODEL` and TTS model/voice are
   account-dependent. Mitigation: env-driven with documented placeholders; `/health` reports
   configuration; no hardcoded model in prompts; clear setup error when unconfigured.
9. **Module-system mismatch.** Adding `"type": "module"` would break CommonJS `server.js`.
   Mitigation: keep server CommonJS and browser files native ESM; do not change package type.
10. **Back-compat of localStorage.** Existing chat keys must survive. Mitigation: retain keys
    unchanged; version migration never touches chat keys; corrupt reads fall back safely.

## 7. Final End-to-End Manual Demo Path

No sign-in required (unless `APP_PASSWORD` is set):

1. Open `/` → **landing** with Chat/Worksheet cards.
2. **Landing → Chat:** `#/chat`; confirm greeting and a correction turn behave as before

4. **Generate:** worksheet renders with French titles and English explanations; no answers or
   transcript in the DOM.

6. **Listen:** play the listening section; replay and slow it; no re-bill on replay/refresh.
7. **Reveal:** show answers + transcript; confirm they appear adjacent.
8. **Send:** "Envoyer au professeur"; feedback renders adjacent with text labels + summary.
9. **Refresh/resume:** reload → same worksheet, answers, audio cache, and feedback restored.
10. **New worksheet:** confirm clearing removes the worksheet, answers, feedback, and cached
    clip; next generation re-bills TTS exactly once.
11. **Failure honesty:** unset a provider key → `/api/generate` and `/api/tts` show actionable
    setup messages and never fabricate content or audio.
